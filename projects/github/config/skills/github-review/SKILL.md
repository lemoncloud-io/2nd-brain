# PR 리뷰 — 의사결정 중심

핵심 질문은 **“명시적 지시 없이 무엇을 결정했고, 그 결정은 요구·근거·권한에 맞는가?”**다.
코드 정확성·회귀·보안 검증도 함께 하되, 모든 줄의 설명보다 결과를 바꾼 결정을 먼저 찾는다.
AI의 내부 추론이나 작성 의도를 추측하지 않고 산출물과 기록에서 관찰되는 선택을 검토한다.

## 언제 쓰나

- PR의 코드·설계·문서 변경을 의사결정 관점에서 리뷰할 때. 사용자 지시 밖의 정책·기본값·범위 변경을 근거와 대조한다.
- 단순 목록 조회나 이미 합의된 문구 교정에는 쓰지 않는다.

## 하지 않는 것

- 기본은 읽기 전용이다. 리뷰 요청만으로 원본 수정·배포·리뷰 게시·승인·머지 권한을 얻지 않는다.
- 상시 감시·무한 재리뷰·자동 후속 알림을 설치하지 않는다(§ 4).
- 에이전트에 운영 쓰기·댓글 게시를 위임하지 않는다(§ 4). 코멘트 요청은 승인 리뷰나 머지 요청이 아니다(§ 결과와 게시).

## 대상과 기준 고정

- 사용자 요청에서 리뷰 대상·목적·수정/게시 범위를 읽는다. PR은 repo·번호·base/head SHA와 최신 diff를 고정한다.
  본문·기존 댓글·테스트 결과가 이전 head를 가리키면 현재 검증으로 계산하지 않는다.
- 요구서·사용자 결정·계약·기존 동작·인용한 코드/공식 문서를 실제로 읽는다.
  코드 호출 이름만 보고 라이브러리 동작을 단정하지 않는다. 원문을 못 읽으면 근거 미확인으로 둔다.
- 사실(현행)·목표 설계·제안·미결을 분리한다. 목표와 코드가 다르다는 이유만으로 코드 결함이라 부르지 않는다.
  목표와 다름을 일치로 표시하거나 실행 조건을 잘못 설명하는 것은 문서 판정 결함으로 다룬다.

## 1. 결정과 권한을 먼저 검토

[리뷰 항목표](references/review-checklist.md)의 결정 원장으로 영향이 큰 선택만 정리한다.
각 결정에는 **바뀐 행동 → 사용자 요구/위임 범위 → 근거 → 영향 → 확인 방법**을 연결한다.

결정의 출처는 다음처럼 구분한다.

- **명시**: 사용자가 정한 것. 맞게 반영됐는지 확인한다.
- **도출**: 합의된 요구·계약에서 따라오는 것. 추가 가정과 반례를 확인한다.
- **구현 재량**: 허용된 범위의 가역적 세부 선택. 지시가 없다는 사실만으로 결함 처리하지 않는다.
- **제안/미결**: 아직 결정권자의 선택이 필요한 것. 확정 사실처럼 쓰거나 구현에 몰래 고정했는지 본다.
- **근거 없음/범위 이탈**: 정책·상품·권한·데이터 수명·비용·외부 공개 등 결과를 바꾼 선택에 근거가 없다.

영향·가역성·허용된 재량을 보고 사용자 재결이 필요한 항목을 좁힌다. 되돌릴 수 있는 통상 구현 선택마다
승인을 요구하지 않는다. 명시된 결정에도 회귀나 계약 충돌이 있으면 근거를 들어 보고한다.

## 2. 여러 결과 지표를 함께 검토

변경에 맞는 지표와 가드레일을 고른다. [지표 표](references/review-checklist.md#지표-기록)로
정확성/품질과 자원·운영 비용의 교환을 확인한다. 속도 하나, 통과 개수 하나로 종합 성공을 선언하지 않는다.

- 성능: 지연·처리량과 메모리·오류율·재시도/요청량 등을 같은 부하·환경에서 비교한다.
- AI 작업: 품질·누락/오탐과 실제 확인 가능한 시간·호출/토큰·재시도·비용을 함께 본다.
  청구 근거 없이 모델별 요금이나 절감액을 추정해 사실로 보고하지 않는다.
- 문서/설계: 요구·결정 추적, 모순·누락, 인용 근거 정확성·후속 인계 가능성을 본다.
  문서에 런타임 성능 지표를 억지로 요구하지 않는다.

각 지표에 baseline·후보·측정 조건/표본·증거·허용 기준·판정을 둔다. 기준이 없으면 제안임을 표시한다.
미측정은 **미측정**, 무관한 항목은 **해당 없음 + 이유**다. 측정 공백은 결함과 별도로 기록하되,
완료 주장이 그 측정에 의존하면 주장 범위를 낮추거나 필요한 검증을 요구한다.
보안·정확성 가드레일 위반을 다른 지표의 향상이나 합산 점수로 상쇄하지 않는다.

## 3. 복잡한 구조는 그림으로 검증

조건 분기·상태 전이·신뢰 경계·비동기 재시도가 판단을 어렵게 하면 Mermaid로 핵심 경로를 그린다.
사소한 문구 수정에는 그림을 만들 필요가 없다.

- 요구/목표와 구현/현행을 구분하고, 같은 그림이면 실선·점선 등의 범례를 둔다.
- 행위자, 판정 주체, 데이터/권한 소유, 호출 방향과 동기/비동기를 표시한다.
- 정상뿐 아니라 거절·실패·중복·취소·복구 경로에서 누가 무엇을 확정하는지 확인한다.
- 노드·간선·판정 조건을 원문 근거와 연결한다. 그림 자체를 검증 증거로 대신하지 않는다.
- 화면 너비에 맞춰 작은 그림으로 나누고, 긴 라벨·교차선을 줄인다. 렌더를 확인하지 않았다면 명시한다.

## 4. 독립 AI 교차 검증

중요 정책·인증/권한·금전·파괴적 데이터 처리·복잡한 비동기 흐름이나 큰 AI 작성 결과는 독립 검증이
도움이 되는 후보이며, 일상적 작은 변경마다 추가 에이전트를 실행하지 않는다.
현재 사용자/환경 지침이 위임을 허용할 때만 적합한 독립 리뷰어를 사용한다.
위임이 금지되었거나 도구·예산이 없으면 **독립 검증 미실시**로 남기고 가능한 직접 리뷰를 계속한다.

- 리뷰어에게 사용자 요구·고정 revision·원문 자료·범위/예산을 먼저 준다. 작성자의 결론이나 예상 결함을
  정답처럼 주지 않는다. 첫 독립 탐색 뒤에만 양쪽 지적을 비교한다.
- [교차 검증 요청 틀](references/review-checklist.md#교차-검증-요청-틀)을 사용해 판단 근거·반례·미확인을 회수한다.
  근거를 재확인해 채택·반박·보류로 판정하고, 단순 합의나 다수결로 사실을 확정하지 않는다.
- 동일 모델이라도 분리된 컨텍스트인지 기록한다. 모델/이름이 다르다는 사실만으로 독립성이 보장되지는 않는다.
- 처음에는 1회 독립 검토와 필요한 쟁점 재확인으로 범위를 잡는다. 새 head·새 근거가 있으면 영향 범위만 재검토한다.
  상시 감시·무한 재리뷰·자동 후속 알림은 설치하지 않는다.
- 에이전트에 운영 쓰기·댓글 게시를 위임하지 않는다. 외부 모델/원격 도구에 민감 원문을 전송할 때는
  기존 허용 범위·데이터 경계를 확인한다.

## 결과와 게시

결과는 중요한 지적부터 쓴다. 각 지적은 **문제·발생 조건·고정 근거·영향·개선 방향·완료 기준**을 포함한다.
개선 제안을 사용자 결정처럼 쓰지 않는다. 재현하지 않은 운영 영향은 조건부로 설명한다.
낮은 확신의 추측, 취향, 이미 명시적으로 보류된 항목을 확정 결함으로 부풀리지 않는다.

필요한 부록만 붙인다: 결정 원장, 지표 비교, 다이어그램, 독립 검증의 이견/미실시 이유.
지적이 없을 수도 있다. **발견한 결함 없음**과 **미검증 위험 없음**은 다르다.
자동 테스트·작성자 자체 확인·주 리뷰·독립 검증·실증·사용자 수용을 서로 다른 상태로 보고한다.

볼트에 지속 보관할 리뷰 결과는 대상 프로젝트의 `outputs/`에 `templates/query-output.md` 형식으로 남기고
프로젝트 README에서 연결한다. repo·PR·검토 base/head·근거·미검증·후속을 기록하며, 볼트 Markdown을
`sources`에 인용할 때는 따옴표로 감싼 wikilink를 쓴다. 리뷰 대상 원본 수정과 결과 기록을 구분한다.
채팅 답변이나 로컬 리뷰 도구의 리뷰안을 모두 볼트 파일로 자동 복제하지는 않는다.

“코멘트 달아줘”처럼 게시가 요청되면, 게시 직전 최신 head와 기존 댓글을 확인하고 바뀐 부분을 재검토한다.
중복 게시를 피하고 고정 SHA·정확한 라인과 검증 한계를 넣는다. 응답이 불명확하면 기존 결과부터 조회한다.
게시 후 코멘트 URL과 내용 반영을 재조회한다. 코멘트 요청은 승인 리뷰나 머지 요청이 아니다.

호출 예: `$github-review PR <번호>를 결정·지표·상태 전이 관점으로 리뷰해줘.`
게시 예: `$github-review PR <번호>를 리뷰하고 확인된 지적을 코멘트로 남겨줘.`
