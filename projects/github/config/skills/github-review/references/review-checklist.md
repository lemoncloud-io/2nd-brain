## 결정 검증 항목

| 항목 | 리뷰 질문 | 확인할 근거 |
| --- | --- | --- |
| 목표·범위 | 요청한 문제를 풀었나? 별도 기능·정책을 끼워 넣었나? | 사용자 지시·수용 기준·실제 diff |
| 결정권 | 명시·도출·구현 재량·제안·미결 중 무엇인가? 제안을 확정으로 승격했나? | 결정 기록·위임 범위 |
| 가정·기본값 | 새 기본값, 제한, fallback, 생략한 검사에 근거가 있나? | 조건문·설정 기본값·관련 계약 |
| 조건·의미 | 실행 전제·예외를 빠뜨렸나? 필드/역할/ID가 계층 간 바뀌나? | 호출부·피호출부·라이브러리 실제 버전 |
| 사실과 목표 | 현행·목표·제안·미결이 구별되나? 일치 판정이 원문과 맞나? | 고정 소스·설계·현황표 |
| 계약·상태 | 요청·응답·권한·취소·복구가 연결되나? 정상과 실패의 최종 상태는 무엇인가? | API 계약·상태 전이·불변식 |
| 비동기 | 재전달과 새 사건을 구별하나? 중복 제거가 후속 정상 전이를 막나? | 멱등 키·이벤트 ID·정렬/재시도·동시성 |
| 데이터·수명 | 무엇을 저장·덮어쓰기·삭제하며 복구할 수 있나? | 소유권·TTL·삭제/롤백 경로 |
| 보안·운영 | 누가 어떤 경계를 넘나? 권한·로그·오류·배포 제약을 바꿨나? | 신뢰 경계·거절 경로·운영 설정 근거 |
| 대안·교환 | 선택 이유와 포기한 성질이 요구에 맞나? 비용을 감췄나? | 비교 근거·결정권자·허용 기준 |
| 검증·주장 | 테스트/모의 결과를 실증·품질·수용으로 표현했나? | 실행 조건·결과·미실시 항목 |
| 인계·메타데이터 | 최신 head와 제목·본문·검증·후속 설명이 같은 범위인가? | PR 파일 목록·SHA·기존 리뷰 revision |

### 결정 원장

| ID | 바뀐 행동/선택 | 구분·권한 근거 | 가정·원문 근거 | 영향·가역성 | 확인 방법·판정 |
| --- | --- | --- | --- | --- | --- |
| D-01 | 관찰한 선택 | 명시/도출/구현 재량/제안·미결/근거 없음 | 요구 ID·고정 파일:라인 | 영향 받는 사람·데이터·비용 | 확인/불일치/미확인 |

AI가 작성했다는 이유만으로 임의 결정이라 부르지 않는다. 반대로 “테스트 통과”는 결정권자의 승인 근거가 아니다.

## 지표 기록

| 축 | 변경에 따라 고를 지표 | 가려지기 쉬운 악화 |
| --- | --- | --- |
| 정확성·품질 | 실패율, 데이터 불일치, 요구 충족, 누락/오탐 | 빠르지만 잘못된 결과, 근거 없는 결론 |
| 응답·처리 | p50/p95 지연, 처리량, 대기 시간 | 평균 개선에 가려진 꼬리 지연·병목 |
| 자원·비용 | peak 메모리, CPU, 요청·토큰 수, 재시도, 확인된 비용 | 속도 개선에 따른 OOM·429·비용 증가 |
| 안정성·운영 | 복구 시간, 중복 실행, 미처리 큐, 장애 영향 | 정상 경로 성능만 좋고 실패 복구 불가 |
| 문서·설계 | 추적 가능한 결정, 모순·누락, 인용 정확성, 인계 가능성 | 문서/도표 개수 증가를 품질로 착각 |

| 지표 | baseline → 후보 | 조건·표본·증거 | 허용 기준(출처) | 판정·한계 |
| --- | --- | --- | --- | --- |
| 관련 지표 | 절대값·단위와 변화량 | 동일 부하·기기·버전·측정 구간인지 | 합의/기존 SLO/제안/없음 | 개선/악화/미측정/해당 없음 |

- 개선율의 분모·단위·표본을 남긴다. 실패한 실행과 반복 측정의 편차를 숨기지 않는다.
- baseline과 후보의 조건이 다르면 직접 비교를 보류한다. 빠진 값·비용·승인 기준을 만들어 채우지 않는다.
- 합의된 기준이 없다면 장단점과 추가 결정 필요성을 보고한다. 수치가 없는 문서 리뷰에 임의 품질 점수를 만들지 않는다.

## 교차 검증 요청 틀

아래 틀은 위임이 허용된 작업에서만 사용한다. 미결인 모델·인원·비용을 임의로 약속하지 않는다.

```text
대상: <repo/PR 또는 산출물>, 고정 base/head: <SHA>
사용자 요구·결정권·리뷰 범위: <원문 또는 정확한 참조>
읽을 원문: <최소한의 고정 diff·계약·의존 구현>
제약: 읽기 전용, 원본/운영/댓글 수정 없음, <시간·호출·자료 범위>

주 리뷰의 결론을 가정하지 말고 독립적으로 확인하라.
명시되지 않은 선택, 조건·권한·상태 전이, 지표 간 악화, 목표와 현행의 혼동을 검토하라.
각 지적에 발생 조건·고정 근거·영향·반례·완료 기준과 확신의 한계를 적어라.
기존에 명시적으로 보류된 항목과 추측은 확정 결함에서 분리하라. 지적이 없을 수도 있다.
실행한 검사·미실시·자료 부족을 구분해서 반환하라.
```

### 이견 처리 기록

| 지적 | 주 리뷰·독립 리뷰 | 직접 확인한 근거/반례 | 판정 |
| --- | --- | --- | --- |
| F-01 | 일치/불일치/한쪽만 발견 | 고정 원문 또는 검증 결과 | 채택/반박/보류, 이유 |

“다른 AI가 동의”를 검증 근거로 쓰지 않는다. 동일 에이전트의 자기 재독은 자체 확인으로 기록한다.
독립 리뷰는 현재 산출물을 교차 확인하는 절차이며, 새로운 스케줄러나 상시 리뷰 서비스를 뜻하지 않는다.

## 보고와 완료 기준

### 지적 한 건

```text
[우선순위] 문제를 나타내는 제목
발생 조건 → 현재 행동 → 요구/계약과의 차이 → 영향
근거: 고정 SHA의 파일:라인, 관련 요구·공식 자료
개선 방향: 제안임을 명시
완료 기준: 어느 조건에서 어떤 관찰 결과여야 하는지
검증 한계: 재현/정적 대조/미실시
```

- P0: 즉시 조치가 필요한 광범위한 중대 문제. P1: 심각한 잘못된 결과/계약 위반으로 빠른 수정 필요.
  P2: 범위가 제한된 정확성·인계 결함. P3: 낮은 영향의 개선. 자료 부족만으로 우선순위를 부풀리지 않는다.
- 판정은 검토한 범위에 한정한다. 수정 권장·재결 필요·추가 검증 필요·발견한 결함 없음을 구분한다.
- 문서 리뷰에서 기존 제품 취약점을 발견했다면 문서의 새 결함과 기존 구현의 미해결 문제를 나눠 보고한다.
- 게시 범위가 요청되었을 때만 댓글/리뷰를 작성하고, 게시 결과 URL을 확인한다.
