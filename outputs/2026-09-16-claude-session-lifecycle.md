# Claude Code 세션 생명주기와 세션 간 통신

## Answer

**세션은 두 종류이고, 둘을 가르는 것은 "프로세스가 어디서 도는가"다.** 이 구분이 끊김·보관
문제의 전부를 설명한다.

| | Remote Control 세션 | 클라우드 세션 |
| --- | --- | --- |
| 실행 위치 | **내 머신의 `claude` 프로세스** | Anthropic 클라우드 VM |
| 계정 기록의 `environment_kind` | `bridge` | `anthropic_cloud` |
| 생성 | `claude --remote-control [이름]`, 세션 안 `/remote-control`, `claude remote-control`(서버 모드), 데스크톱 앱 | claude.ai/code, `claude --cloud "작업"`, 데스크톱 앱의 "Continue in web" |
| 생존 조건 | **로컬 프로세스가 살아 있어야 한다** | 서버가 보관. 비활성으로 VM이 회수돼도 재오픈 시 대화 복원 |
| 브라우저·폰 닫기 | 영향 없음 | 영향 없음 |
| 터미널·앱 종료 | **수 초 내 offline** | 영향 없음 |
| 로컬 파일·MCP 접근 | 가능 (내 머신이므로) | 불가 (격리된 VM) |

**끊김·보관의 원인은 세 가지다.**

1. **프로세스 소유자가 앱이면 앱이 세션을 끝낸다.** 데스크톱 앱이나 Agent SDK 호스트가 만든
   세션은 그 호스트가 세션을 소유한다. 작업이 끝나 해당 대화를 닫으면 호스트가 세션을 종료하고
   서버는 `archived`로 표시한다. 버그가 아니라 설계된 생명주기다.
2. **머신이 잠자기·오프라인이면 재연결 창이 닫힌다.** 문서상 잠자기·네트워크 단절은 자동
   재연결 대상이지만, 그 사이 호스트가 대화를 닫았다면 1번 경로로 보관된다. 계정 기록에는
   `computer_unreachable`로 남는다.
3. **대화가 재작성되면 이전 세션이 정리된다.** 컴팩션이 대화를 다시 쓰거나 `/resume`으로 대화를
   바꾼 뒤 재연결하면, 쓰던 서버 세션은 목록에 남기지 않고 `archived`로 정리된다. 서버 모드를
   `--no-create-session-in-dir`로 띄웠다가 멈춰도 마찬가지다.

**해결책 (효과 순).**

1. **상주 프로세스로 띄운다.** 앱이 아니라 `tmux`(또는 `screen`) 안에서 `claude remote-control`
   (서버 모드) 또는 `claude --remote-control <이름>`. 터미널·앱을 닫아도 프로세스가 남는다.
2. **잠자기를 억제한다.** 랩탑이라면 `caffeinate -is <명령>`처럼 에이전트를 자식 프로세스로 감싼다
   (Linux는 `systemd-inhibit`). 상주 데스크톱 머신은 불필요.
3. **보관됐어도 되살린다.** 같은 디렉터리에서 `claude remote-control --session-id <id>` — 서버가
   멈춘 뒤 **약 4시간** 창 안에서 동작하고, v2.1.228+ 는 보관된 세션도 자동으로 보관 해제한다.
   대화형으로 띄웠던 세션은 `claude --continue` 또는 `--resume`으로 대화를 다시 열면 기존 세션에
   재부착된다. 세션 ID는 세션 URL의 `/code/` 뒤 부분이다.
4. **항상 살아 있어야 하는 작업은 클라우드 세션으로 보낸다.** 대신 로컬 파일·MCP는 못 쓴다.
5. "기본으로 원격 제어 켜기" 설정은 **자동으로 켜 줄 뿐 생존을 보장하지 않는다.** 프로세스가
   죽으면 똑같이 offline이다.

## Evidence

### `/rc`와 `--remote-control`은 결과가 같다 — 진짜 분기는 서버 모드

세션 안에서 `/remote-control`(`/rc`)로 켜는 것과 기동 시 `--remote-control`(`--rc`)로 켜는 것은
**같은 것을 만든다**: "지금 이 대화형 프로세스에 원격 세션 하나를 붙인다". 차이는 켜는 시점과
대화 이력 승계 여부뿐이고, **끊기는 조건은 완전히 동일하다.** 공식 문서도 `claude remote-control`,
`claude --remote-control`, `/remote-control` 셋을 같은 층에 놓고 설명한다.

| | 대화형 + RC (`--rc` / `/rc`) | 서버 모드 `claude remote-control` |
| --- | --- | --- |
| 로컬에서 타이핑 | 가능 | 불가 (원격 대기 전용) |
| 프로세스당 원격 세션 | 1개 | 여러 개 (폰·웹에서 계속 열 수 있음) |
| Ctrl+C로 멈추면 | offline → `--continue`·`--resume`으로 재부착 | **보관되지 않음** → 같은 디렉터리에서 재실행하면 전부 복귀 (~4시간 창) |
| 세션 크래시 | 프로세스가 죽으면 끝 | **프로세스가 죽으면 원격 메시지만으로는 복구되지 않음** |
| 네트워크 장기 단절 | 로컬 작업 계속, 복귀 시 자동 재연결 | 약 10분 후 프로세스 종료 |
| 대화 이력 | `--rc`는 새 대화부터 · `/rc`는 기존 이력 승계 | 세션별로 독립 |

권장 조합은 상주 멀티플렉서 + 잠자기 억제 + 서버 모드다:

```bash
tmux new -d -s <세션명> -c <작업디렉터리> \
  'caffeinate -is claude remote-control --remote-control-session-name-prefix <접두사>'
```

`--remote-control-session-name-prefix`를 주면 자동 생성 이름에 접두사가 붙어 계정 목록에서
구분하기 쉽다. 붙인 이름이 곧 다른 세션이 부르는 주소가 된다.

### 세션 간 통신은 경로가 둘이고, 클라우드는 단방향이다

절차의 정본은 `claude-remote-session` 스킬이다. 요지만 옮기면:

- **경로 1 (로컬 소켓)** — 같은 머신의 세션끼리. 세션이 기동 시 자기를 등록하고, 메시지는 유닉스
  도메인 소켓으로 직접 간다. 네트워크를 타지 않으며 접근 통제는 파일 권한이다.
- **경로 2 (계정 브리지)** — 다른 머신·클라우드. `--remote-control`로 등록된 세션끼리 계정 단위로
  서로 보인다. SSH나 같은 네트워크가 필요 없다.
- `ListAgents`로 발견하고 `SendMessage`로 보낸다. 회신은 자동으로 도착하므로 폴링하지 않는다.
- **클라우드 세션은 수신만 되고 회신은 못 한다.** 결과는 그 세션의 transcript에서 확인한다.
- 목록은 스냅샷이며 전부가 아니다 — 등록되지 않은 세션, 보관·offline 세션은 보이지 않는다.

세션 ID로 직접 찌르는 경로도 있다: 로그인된 터미널에서 `claude -p "<메시지>" --cloud <session-id>`.
메시지 한 건을 큐에 넣고 즉시 종료하며, 세션을 시작한 머신이 아니어도 된다. 보관된 세션은 메시지를
거부하므로 먼저 보관을 해제해야 한다.

### 실측 — 클라우드 세션에서 브리지 세션을 깨울 수 있는가 (2026-09-04)

클라우드 세션 한 개에서 네 가지 경로를 모두 시도했고 **전부 실패**했다.

| 시도 | 결과 |
| --- | --- |
| `ListAgents`로 피어 탐색 | 도달 가능한 세션 0 — 브리지에 살아 있는 세션이 없었다 |
| 보관된 브리지 세션을 보관 해제 | `ARCHIVED` → `PENDING`으로 바뀌었으나 `disconnected` 유지 |
| 대상 세션에 묶은 Routine을 즉시 발사 | **`session_gate_denied`** — 생성은 되나 발사가 서버에서 막힌다 |
| 컨테이너 CLI로 `claude -p --cloud <id>` | `Session expired` — 컨테이너의 CLI 로그인은 이 송신에 필요한 범위의 토큰이 아니다 |

**결론: 보관 해제는 서버 쪽 상태만 바꾼다.** 세션을 실제로 되살리는 것은 그 머신의 `claude`
프로세스가 다시 붙는 일이고, 그것은 원격에서 대신해 줄 수 없다. 깨우는 동작은 세션이 돌던
머신에서 해야 한다 — 앱에서 그 대화를 다시 열거나, 터미널에서 `claude remote-control --session-id <id>`.
예외는 하나뿐이고 조건이 좁다 — **서버 모드 프로세스가 살아 있는 상태에서 그 아래 세션 하나가 죽은
경우**라면 폰이나 웹에서 메시지를 보내는 것으로 서버가 그 세션을 다시 서빙한다. 서버 프로세스 자체가
죽었다면 이 예외는 적용되지 않으며, 그때는 그 머신에서 프로세스를 다시 띄우는 수밖에 없다.

## Notes

- 표의 "생존 조건"·"터미널 종료 시 offline"은 공식 문서 § Limitations의 서술("Remote Control runs
  as a local process… the session goes offline until you bring it back")에 근거한다. 약 4시간
  복귀 창, 서버 모드의 약 10분 네트워크 타임아웃도 같은 문서의 수치다.
- 실측 표의 4건은 2026-09-04에 클라우드 세션 한 개에서 직접 시도한 결과다. `session_gate_denied`는
  그때 받은 오류 코드 그대로이며, 이 게이트의 적용 범위(어떤 조합에서 허용되는지)는 확인하지 않았다 —
  이 결론은 "클라우드 세션에서 다른 세션으로 Routine을 발사하는 조합"에 한정된다. needs-update.
- 브리지의 네트워크 전송 상세(엔드포인트·프로토콜)는 확인하지 않았다. "계정 서비스 경유"까지가
  근거 있는 진술이다.
- 세션 이름은 상대 쪽에서 바뀔 수 있고 종료되면 목록에서 빠진다. 기억해 둔 이름을 재사용하지 말고
  매번 다시 발견한다.
- **개인 노트를 클라우드 세션의 `private/`에 두지 않는다.** git 비추적이므로 VM이 회수되면 함께
  사라진다. 이 문서의 원본 조사 기록이 실제로 그렇게 소실됐고, 그 내용을 정제해 다시 쓴 것이 이
  문서다. 클라우드 세션에서 남길 가치가 있는 것은 커밋되는 경로에 둔다.
